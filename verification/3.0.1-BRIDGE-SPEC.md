# Executable spec — local MCP authentication bridge for 3.0.1

Tier: **3 (authentication, secret handling, and public installer behavior)**

Spec approval: **not obtained (autonomous run)** — the user requested “fix bridge login đi”; this file is the post-hoc review artifact for the concrete contract below.

## Failure model

| Failure mode | Harm | Executable defence |
|---|---|---|
| Claude's runtime cannot reach staging while the user's Chrome can | The existing helper cannot log in and Claude repeatedly asks the tester to type credentials | A local MCP wrapper starts Playwright MCP in extension mode and runs the login hook in the local MCP process |
| Credentials from `.env` pass through the model, tool arguments, stdout, or stderr | Secret disclosure | The init hook reads values locally; the wrapper passes only variable names and the secrets-file path, disables unsafe debug modes, and redaction tests use sentinel credentials |
| A hostile or unrelated page resembles a login form | Credentials are submitted to the wrong origin | Exact configured login URLs are mandatory; non-matching URLs are ignored even when their DOM is identical |
| Claude guesses that a configured credential “looks like the wrong account type” | Valid credentials are never attempted | Skill contract requires one bridge/helper attempt and forbids format-based credential inference |
| A CMS requires a role dropdown before username/password | Login remains blocked despite valid credentials | Optional non-secret select selector/value runs before credential fields are filled |
| Username and password render in separate steps | The bridge fills only the first field or clicks the wrong action | Integration test covers username → Next → delayed password → Submit |
| TOTP appears after password submission | Pre-auth state is mistaken for success | The bridge waits for the configured/default OTP surface, generates current TOTP locally, and submits it before success |
| Playwright or Node debug logging captures fill values or the child environment | Secrets leak outside application-level redaction | Inherited Playwright debug modes are removed and `NODE_DEBUG`/`NODE_DEBUG_NATIVE` fail closed before MCP spawn |
| The Playwright extension bridge connects automatically to the wrong target/profile or silently changes upstream behavior | The wrapper appears zero-touch while it is not | Pin the supported Playwright MCP version, make extension mode explicit, expose pass-through arguments only after `--`, and document the one-time extension/token setup separately from per-login automation |

## Acceptance scenarios

```gherkin
Feature: Login through a local Playwright MCP bridge without exposing credentials

  Scenario: Local one-step login
    Given an exact configured login URL and a dotenv file containing TEST_USER and TEST_PASS
    And the local MCP-controlled page can reach that URL
    When the page reaches the login form
    Then the bridge fills username and password and submits the form
    And no credential value appears in bridge output

  Scenario: Select a CMS role and complete a delayed two-step login
    Given an exact configured login URL
    And a configured role selector/value
    And password appears only after username and Next
    When the page reaches the login form
    Then the bridge selects the role, fills username, clicks Next, waits for password, and submits

  Scenario: Complete TOTP locally
    Given password login redirects to a TOTP challenge on an explicitly configured auth URL
    And the dotenv file contains TEST_TOTP_SECRET
    When the challenge appears
    Then the bridge generates and submits a current or adjacent-window six-digit code locally
    And neither the TOTP secret nor generated code appears in output

  Scenario: Ignore a lookalike page
    Given a page on a URL not present in the exact login URL list
    And that page contains identical username, password, and Login controls
    When the bridge observes the page
    Then it does not fill, select, click, or submit anything

  Scenario: Start the local MCP process safely
    Given a readable dotenv file, exact login URL, and variable names
    When the wrapper is run in dry-run mode
    Then it reports a command pinned to the supported @playwright/mcp version
    And the command includes --extension, --init-page, and --secrets
    And it never prints dotenv values

  Scenario: Reject unsafe bridge configuration
    Given a missing dotenv file, a non-HTTP login URL, missing credential variables, or inherited NODE_DEBUG
    When the wrapper or init hook starts
    Then it fails closed before credentials are submitted or MCP is spawned
```

## Negative constraints

- Never read, print, return, or pass a credential value in an agent-visible command/tool argument.
- Never fill credentials based only on a matching form; exact configured login URLs are required.
- Never weaken production/side-effect gates. The bridge only authenticates; it grants no permission for later writes.
- Never silently fall back to asking for a password after `.env` is configured. Report the concrete bridge failure and its unlock condition.
- Never infer credential validity or account type from variable names, length, character class, or UI labels; only an actual authentication result can reject them.
- Preserve the existing `auth-login.mjs` path for runtimes that can reach the target.
- Preserve Codex and Claude installer behavior and keep runtime dependencies empty.
- Do not modify the user's Claude/MCP configuration, install the browser extension, publish npm, tag, commit, or push in this run.
