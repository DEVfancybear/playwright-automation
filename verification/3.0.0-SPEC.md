# Executable release spec — playwright-automation 3.0.0

Tier: **3 (authentication and public installer behavior)**
Spec approval: **not obtained (autonomous release run)** — this file is the post-hoc artifact to review.
Requested release action: bump to `3.0.0`, commit, and push the current branch. Do not create a tag or publish npm in this run.

## Failure model

| Failure mode | Harm | Executable defence |
|---|---|---|
| A stale session opens a login form only after SPA hydration | Agent falsely reuses an expired session and every later test is unauthenticated | Browser integration test with a delayed login surface |
| OTP UI appears after the password submit navigation | Agent stores a pre-auth state and reports login success without completing MFA | Browser integration test that requires an OTP submit before issuing the session cookie |
| A normal landing page contains a promo/product/postal-code input | Agent mistakes business data for OTP, fills it with TOTP, or rejects a valid session | Browser integration test with `promoCode` on the authenticated dashboard |
| A two-step form uses custom nonstandard selectors | A supplied password selector is treated as present before it is visible, so the Next button is never clicked | Browser integration test with delayed custom password field |
| Credential/TOTP values reach stdout, stderr, arguments, or committed files | Secret disclosure | Output assertions, diff scan, package-content check, and no value-bearing CLI options |
| Playwright debug logging prints `fill(<secret>)` before helper error handling | Secret disclosure despite application-level redaction | Helper neutralizes inherited Playwright debug modes before import; DEBUG-env password/TOTP regressions |
| A bare 401/403/5xx page has no login form | Session check falsely treats an error page as authenticated | Terminal HTTP status rejection in browser integration tests |
| One storageState path is reused after changing the requested login target | Old sidecar landing URL is trusted and the new target is never opened/logged in | Sidecar login identity binding and cross-target regression |
| A custom installer target points at unrelated or broad data | `--force`/`uninstall` recursively removes a workspace, home, filesystem root, or unrelated files | Removal target guard plus identity and sentinel-preservation tests |
| Global Codex install targets legacy `~/.agents/skills` | Agent keeps loading the old skill and continues refusing the new autonomous flow | CLI path tests for configured and fallback Codex homes; project path remains `.agents/skills` |
| npm-installed copy is documented as a git clone | `git pull` fails and users cannot update the active skill | Documentation assertion for `install --codex --force` |

## Acceptance scenarios

```gherkin
Feature: Safe autonomous login and correct Codex skill installation

  Scenario: Refresh a delayed stale session
    Given storageState contains a stale cookie
    And the login form appears 700 ms after DOMContentLoaded
    When auth-login runs in ensure mode
    Then it must detect the form, log in, and save a valid session
    And it must not print the username, password, or TOTP secret

  Scenario: Complete delayed TOTP
    Given password authentication redirects to an OTP page
    And the OTP input appears 700 ms later
    When TEST_TOTP_SECRET is available
    Then auth-login must submit the current or adjacent-window six-digit TOTP before reporting success
    And the saved session must contain the final authenticated cookie

  Scenario: Ignore business code fields
    Given a successful login lands on a dashboard containing input name promoCode
    When auth-login verifies the new or reused session
    Then promoCode must not be classified or filled as an authentication challenge

  Scenario: Support a custom two-step form
    Given username, Next, password, and submit use explicit custom selectors
    And the custom password field appears only after Next
    When auth-login runs with those selector names
    Then it must click Next, wait for the password field, and authenticate

  Scenario: Resolve Codex global and project locations
    Given CODEX_HOME is configured
    Then the global target must be CODEX_HOME/skills/playwright-automation
    Given CODEX_HOME is absent
    Then the global target must be ~/.codex/skills/playwright-automation
    And the project target must remain <cwd>/.agents/skills/playwright-automation

  Scenario: Ship a self-consistent package
    When the npm tarball is inspected
    Then version must be 3.0.0
    And SKILL.md, openai metadata, autonomous guidance, installer, auth helper, and explorer must be present
    And Python bytecode or __pycache__ must not be present
```

## Negative constraints

- `relaxed` lowers interaction gates only; it must not authorize production writes, real money, real outbound messaging, CAPTCHA bypass, or access to other users' data.
- Credentials remain values loaded inside the helper from environment or `.env`; the Agent passes variable names only.
- `explore.mjs` must not regain inline username/password flags.
- The eight-stage testing pipeline remains mandatory; `CONFIRM` becomes a recorded self-approval only for safe relaxed-mode scope.
- Project-scoped Codex installation remains `.agents/skills`; the installer never deletes a legacy global copy automatically.
- Existing Claude install paths and commands remain compatible.
- No npm tag or publish is part of this release action.

- Add exact dev dependency `@playwright/test@1.62.1` solely for repeatable local browser integration tests; no runtime dependency is added.
- Use Node's built-in test runner; add no test framework.

## Revision 1 — explicit Claude Code support

User addition: **"support cả claude code nữa nhé"**.

- Global Claude Code target remains `~/.claude/skills/playwright-automation`.
- Project-scoped Claude Code target remains `<cwd>/.claude/skills/playwright-automation`.
- `install`, `install --force`, `where`, and `uninstall` must work with explicit `--claude`; the no-host-flag default stays Claude-compatible for backward compatibility.
- The same `SKILL.md`, autonomous-login helper, relaxed/guarded rules, references, and scripts are copied for Claude Code; only `agents/openai.yaml` is Codex-specific metadata and is harmless in the shared payload.
- Add CLI regression coverage for both Claude paths and documentation coverage for the Claude `--force` update command.

## Revision 2 — username-only SSO challenge and scoped uninstall guidance

- Session validation must treat a visible username/account field paired with Login/Next as an auth challenge even before a password field exists; otherwise an expired two-step SSO session can be falsely reused.
- When installation already exists, the remediation command must preserve both the selected host (`--codex`/`--claude`) and scope (`--project`/`--dir`) so it cannot uninstall a different copy.

## Revision 3 — generic short prompt expands to the complete workflow

User clarification: a prompt shaped like **“open `<staging-login-url>` and test `<feature/screen>`”** is an end-to-end test objective, not an EXPLORE-only navigation request.

- On a confirmed non-production target, both Codex and Claude Code must infer and continue through browser launch → `.env`/secret-store auto-login → live exploration → safe self-approved plan → test generation → execution/healing → evidence report.
- The Agent must not ask the tester to restate those stages or manually log in when the configured helper can do it.
- The example URL, feature, selectors, credential names, and product flow must remain runtime inputs. No product/domain-specific value may be hard-coded into this skill.
- An explicit narrow request such as “only open the page” or “only take a screenshot” still controls scope.

## Revision 4 — destructive installer guard and auth false-positive controls

- `install --force` and `uninstall` must refuse filesystem roots and any target equal to or containing the user home, current working directory, or source package.
- An explicitly supplied empty/whitespace `--dir` must fail; it cannot fall back to a global target.
- A removable target must contain a `SKILL.md` whose frontmatter declares `name: playwright-automation`; unrelated files must survive both commands unchanged.
- An unverified existing `--dir` target must not receive a copy-paste destructive uninstall hint.
- Username/account only counts as an auth challenge when paired with a named Login/Log in/Sign in/Next/Continue action in the same form when a form exists, or with an explicit selector. A business Account form plus an unrelated Continue button must not invalidate a session.
- The OTP integration server must validate the submitted value as the actual current or adjacent-window TOTP, rather than accepting any POST body.

## Revision 5 — debug leak, HTTP fail-open, and target-bound session metadata

- Before Playwright is dynamically imported, the auth helper must remove inherited diagnostic modes (`DEBUG`, `DEBUG_FILE`, `PWDEBUG`, `PWDEBUGIMPL`) that can print secret-bearing API calls outside the helper's redaction boundary. Any nonempty `NODE_DEBUG`/`NODE_DEBUG_NATIVE` must fail closed before browser spawn because Node caches wildcard debug settings at process startup.
- Session verification must reject terminal HTTP responses with status 400 or greater even if the page contains no recognized auth form.
- Stored `landingUrl` is trusted only when stored `loginUrl` has the same exact normalized `URL.href` as the current `--url`, preserving userinfo, pathname/trailing slash, query, and hash; otherwise verification starts from the requested URL.
- Mutation evidence is valid only when the exact intended test is the failing TAP entry. A different failure elsewhere in the suite cannot count as a killed mutant.
- The release gauntlet must validate staged-only state at both start and finish and require an unchanged `git write-tree` fingerprint, so a shared-workspace edit cannot produce evidence for content different from the commit candidate.
